## 一、化約規則定案（Erick 2026-10-25 確認）

> **主命數只有一個數字。計算結果出現兩位數就繼續逐位相加，直到剩一位數。**

**不設大師數。11、22、33 一律繼續化約。**

例：`19970120` → 29 → 11 → **2**，路徑寫成 `+29/11/2`，終值是 2 不是 11。

此規則與 Excel 黃金樣本、lifeos、以及你已完成的模組**一致**。你的 366/366 通過的正是這個規則，不需要改動。

## 二、n8n `命盤計算引擎 v1.0` 實查結果

Workflow id `MfYvLJG42Zx3TDJH`，`active: true`，單一 Python Code 節點。你先前無法讀取，由我方代查。

### 2-1 ⚠ 更正《00-交接》第 1-4 節的說法

該節寫「計算實作其實有四套，階段 1 的對拍必須把它一起納入」——**這個說法不精確**。

這支引擎**不計算流年、流月、流日**。它算的是主命數、身心靈三角形（主／中年／老年）、先天數、後天數、缺數、過多數。

正確的盤點是：

| 計算 | 實作數 | 狀況 |
| --- | --- | --- |
| 流年／流月／流日 | **3 套** | 你的新模組、lifeos、nas-annual-engine。n8n 不算這個 |
| 主命數與化約 | **4 套** | 多了 n8n 這支，且它的化約規則錯誤（見 2-2） |
| 農曆轉換 | **3 套** | 你的新模組（正確）、lifeos（2031+ 錯）、n8n（表正確但解析器壞） |

所以流年流月流日的對拍仍是三方，不是四方。主命數的對拍才需要納入 n8n。

### 2-2 n8n 的化約違反定版規則

```python
while temp > 9:
    if temp in [11, 22, 33]:
        final_digit = temp
        break          # ← 停在大師數，與定版不符
```

依第一節定案，**這段 `if` 必須移除**，一路化約到個位數。

此外它的路徑字串組法也與定版不同：`calc_life_triangle` 先把年月日各自digit-sum 再相加，再丟進 `calc_numerology_path` 二次相加，導致路徑顯示少一層（例如顯示 `+4` 而非 `+31/4`）。終值在無大師數的情況下仍相同，但**顯示格式不一致**，若此引擎的輸出會呈現給使用者，需一併對齊。

### 2-3 ⚠ n8n 的農曆功能從未運作過（現行線上 bug）

```python
def parse_lunar_db(raw_data):
    parts = [p.strip() for p in line.split(',')]
    if len(parts) < 5: continue
    year = int(parts[0])        # parts[0] = "1900: { 'new_year': '1900-01-29'"
    ...
    except: continue
```

`LUNAR_DATA_RAW` 是 Python dict 字面值格式，解析器卻按 CSV 切。每一行的 `int(parts[0])` 都丟例外，被 `except: continue` 靜默吃掉。

**結果：`LUNAR_DB` 恆為空字典**，`solar_to_lunar` 一律回傳 `{'error': True, 'str': '農曆資料庫未載入'}`，`lunar_triangle` 恆為 `None`，報告中永遠印出「🌙 農曆：農曆資料庫未載入」。

程式中尚留有 `# ↑↑↑ 請將您的完整農曆資料（1900-2100）貼在上面 ↑↑↑` 的佔位註解。

**這支 workflow 是 active 狀態，且為 `executeWorkflowTrigger` 子工作流。** 接手時請先查出有哪些工作流呼叫它，評估影響範圍——可能有其他產品一直拿不到農曆資料而沒人發現。

### 2-4 ✅ 但它的農曆表是正確的

逐筆比對 2031、2033、2042、2049、2100 全部與 Excel 一致，且同樣涵蓋 1900–2100。

即：**lifeos 缺的那段正確資料，n8n 這支本來就有，只是解析不出來。**

不過你不需要從這裡取——`lunar-vectors.json` 的 `table` 欄位就是權威版本（已修正 1900 那一筆）。n8n 的 1900 寫成 `1900-01-29`，與真值 `1900-01-31` 差兩天，同樣要修。
