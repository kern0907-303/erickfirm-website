## 一、定版規則

三者都是組出八碼字串後逐位相加、再逐層歸約到個位數。

| | 組成 | 轉換點 |
| --- | --- | --- |
| **流年** | **目標年** ＋ 生日月 ＋ 生日日 | **生日當天** |
| **流月** | 生日年 ＋ **目標月** ＋ 生日日 | **每月生日的那一日** |
| **流日** | 生日年 ＋ 生日月 ＋ **目標日** | **每日零時**（無偏移） |

記法：**流年改年、流月改月、流日改日**，其餘兩段固定取自生日。

### 跨界回退

- **流年**：目標日的「月日」若 **小於** 生日的「月日」，目標年減 1。
- **流月**：目標日的「日」若 **小於** 生日的「日」，目標月減 1；為 0 時回捲為 12。
  - 回捲為 12 時**年份段不變**（仍是生日年），因為流月的年份段本來就固定取生日年。
- **流日**：不回退。

### 陽曆陰曆

**規則完全相同。** 差別只在：陰曆要先把目標日轉換成農曆日期，再套同一組公式；生日也用農曆生日。

### 教學口徑

對學員的說法：**以生日的「月」與「日」作為跨年、跨月的置換依據。**

### 驗算範例（生日 1997-12-20）

| 目標日 | 流年 | 流月 | 流日 |
| --- | --- | --- | --- |
| 2010-01-01 | `20091220` → 16 → **7** | `19971220` → 31 → **4** | `19971201` → 30 → **3** |
| 2010-01-20 | `20091220` → 16 → **7** | `19970120` → 29 → 11 → **2** | `19971220` → 31 → **4** |
| 2010-12-19 | `20091220` → 16 → **7** | `19971120` → 30 → **3** | `19971219` → 39 → 12 → **3** |
| 2010-12-20 | `20101220` → 8 → **8** | `19971220` → 31 → **4** | `19971220` → 31 → **4** |

第 1 列與第 2 列之間只差流月（1/20 換月），第 3 列與第 4 列之間流年與流月同時換（12/20 是生日）。

## 三、修正一：lifeos（Cloudflare Worker）

**檔案：** `lifeos` Worker 的 `calcFlowsWithTarget`

**問題：** 流月的年份段用了 `fyBase`（當期流年年份），應為 `birthY`（出生年）。

```js
// 現況（錯）
const fmStrRaw = String(fyBase) + String(fmBase).padStart(2, "0") + String(birthD).padStart(2, "0");

// 修正
const fmStrRaw = String(birthY) + String(fmBase).padStart(2, "0") + String(birthD).padStart(2, "0");
```

**只改這一處。** 流年（`fyStrRaw`）、流日（`fdStrRaw`）、以及 `fmBase` 的月份回退邏輯**都已正確，不要動**。

**驗證結果：** 套用此修正後重跑同一批 672 筆樣本 → **三項全中 672/672（100%）**。

## 四、修正二：nas-annual-engine 的流月

**檔案：** `app/calculation/annual_months.py`

```python
# 現況（錯兩處）
solar_flow = path_for(f"{year}{month:02d}{birth.day:02d}", "+")
```

錯誤：
1. 年份段用日曆年 `year`，應為出生年 `birth.year`
2. 月份沒有做「目標日 < 生日日 → 月份減 1」的回退

```python
# 修正
flow_month = month if target_day >= birth.day else (month - 1 or 12)
solar_flow = path_for(f"{birth.year:04d}{flow_month:02d}{birth.day:02d}", "+")
```

**注意：** 現行 `build_month_snapshots` 是以「日曆月」為單位產生 12 筆快照，不帶目標日。要做回退就必須決定每筆快照代表哪一天。兩種處理：

- **（建議）改成輸出流月區段**：第 N 段 = 從 `(N月, 生日日)` 到 `(N+1月, 生日日 - 1)`，每段一個流月數字，整年 12 段。這與定版規則完全對齊，也不會有一個日曆月兩個數字的問題。
- 若必須維持日曆月為單位：每個日曆月要輸出**兩段**（1 日～生日日前一天用上個月的流月，生日日～月底用本月的流月）。

陰曆流月同樣要改：現行用「該日曆月佔最多天的農曆月」（`dominant`），應改為依定版規則取農曆目標月並做同樣回退。

## 五、修正三：nas-annual-engine 的流年

**檔案：** `app/calculation/numerology.py`

```python
# 現況（錯）
def flow_for(year: int, month: int, day: int, sign: str) -> dict[str, Any]:
    result = source.calc_flows_detailed(year, month, day, year, 12, 31, sign)
```

目標日被寫死成 `(year, 12, 31)`。因為 `(12, 31)` 永遠大於或等於任何生日，**生日回退條件永遠不會觸發**，整個日曆年都套用「生日之後」那一段流年。

以 12-20 生日的人為例，1/1 到 12/19 共 **354 天的流年是錯的**。

**修正方向：** `flow_for` 必須接受真實的目標日，或改為回傳該日曆年的**兩段流年**：

- 第 1 段：1/1 → 生日前一天，流年 = `(year-1) + 生日月 + 生日日`
- 第 2 段：生日 → 12/31，流年 = `year + 生日月 + 生日日`

2027 報告以日曆年為容器，因此**必須呈現兩段**。這正是報告的個人化賣點——轉折日每個人都不同。

### 陰曆轉換層（已驗證）

檔案：`lunar-vectors.json`

Excel 的「農曆計算基礎」工作表 `A2:C202` 存放農曆對照表，欄位為 `年 / 公历日期 / 闰月|依次大小月`——**與 lifeos 的 `LUNAR_DB` 是完全相同的資料格式**，確認為同一套來源。

| | 範圍 |
| --- | --- |
| Excel 表 | **1900–2100**（201 年） |
| lifeos `LUNAR_DB` | 1900–2050（151 年） |

**全表健全性檢查：** 用 Excel 表跑 1900–2099 每個農曆年的最後一天，必須落在 12月29 或 12月30 → **200/200 通過**。

**Excel 檔內註記的三個閏月案例全部重現：**
`19870729` → 1987年閏6月4日｜`19980629` → 1998年閏5月6日｜`20120529` → 2012年閏4月9日

#### ⚠ 發現一：lifeos 的農曆表從 2031 年起是錯的

以「每個農曆年最後一天」逐年打線上 API 對拍（150 筆）：

| 區間 | 結果 |
| --- | --- |
| 1901–2030 | ✅ 全數相符 |
| **2031–2049** | ❌ **16 筆不符** |

錯誤樣態包含不可能的輸出：

```
20330130  正確=2032年12月30日   lifeos=2032年13月1日   ← 13 月
20320210  正確=2031年12月29日   lifeos=未知
20350207  正確=2034年12月30日   lifeos=2034年12月29日  ← 差一天
```

**成因：** new_year 日期全部正確，但 **2031 年起的月長碼（code）與閏月號是錯的**。例如：

| 年 | 正確（Excel） | lifeos 現況 |
| --- | --- | --- |
| 2031 | `03\|0110101101010` | `03\|0110110101000` |
| 2033 | `11\|0100101011101` | `11\|0100101011010` |
| 2042 | `02\|0100101011011` | `06\|0100101011100` ← 連閏月號都錯 |
| 2049 | `00\|1010110110100` | `00\|0100101011010` |

**影響評估：**

- **陰曆主命數**（換算出生日）：**安全**。在世者皆生於 2031 年前。
- **陰曆流年／流月／流日**（換算「今天」）：**2030-12-31 前正確，2031 起全錯。**
- **2027 流年報告：不受影響**（2027 在乾淨區間）。

不是立即起火，但是定時裝置。既然要重建計算模組，直接改用 Excel 的完整表（到 2100），順便把範圍從 2050 延長 50 年。

#### ⚠ 發現二：1900 年需要修正一天

Excel 存的 1900 年 new_year 是 `1900-01-30`，但實際該年農曆初一是 **1900-01-31**。這是 Excel 日期系統的 1900 閏年臭蟲（誤將 1900 當閏年，3/1 之前的日期少一天）。

**lifeos 這一格是對的**（`1900-01-31`）。移植 Excel 表時**必須修正 1900 這一筆**，其餘 200 筆照抄。`lunar-vectors.json` 裡的表已套用此修正。

#### 向量內容

428 筆，含三個閏月案例、農曆年界前後日、1900 與 2099 邊界，以及 1900–2099 每一年的初一與除夕。
