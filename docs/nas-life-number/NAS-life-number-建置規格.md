## 1. 三個必須先解決的問題

### 1-1 流年／流月／流日計算已證實存在歧異（阻斷項）

流年／流月／流日的實作需檢視 `lifeos`（JS）、`nas-annual-engine`（Python）與其來源專案 `soul-dashboard`。n8n 的 **`命盤計算引擎 v1.0`**（`MfYvLJG42Zx3TDJH`）計算陽曆／農曆命盤，不計算流年／流月／流日，不列入這項實作數量或對拍。

**實測結論**（672 筆樣本：8 組生日 × 84 個目標日）：

| 實作 | 流年 | 流月 | 流日 |
| --- | --- | --- | --- |
| Excel 123諮商版（權威） | ✅ 366/366 | ✅ 366/366 | ✅ 366/366 |
| lifeos | ✅ 100% | ❌ 18% | ✅ 100% |
| nas-annual-engine | ⚠️ 僅生日後那段正確 | ❌ 12% | — 未計算 |

**下表的兩套流年／流月／流日實作對流月給出不同答案。** 使用者在免費頁與付費報告看到不同數字，是會退費的等級。672 筆對拍表涵蓋 Excel 黃金樣本、lifeos 與 nas-annual-engine；不包含 n8n 命盤計算引擎。

另有一處取法不同：陰曆流月，engine 用該日曆月內佔最多天的農曆月（`dominant`）為基準，與定版規則不符。

**已定案（2026-10-24，Erick 口述確認）**，完整說明與四處修正見另一份文件《流年流月流日-定版規則與修正》：

| | 組成 | 轉換點 |
| --- | --- | --- |
| 流年 | **目標年** ＋ 生日月 ＋ 生日日 | 生日當天 |
| 流月 | 生日年 ＋ **目標月** ＋ 生日日 | 逐日套用定版公式，以流月來源月變化日為邊界 |
| 流日 | 生日年 ＋ 生日月 ＋ **目標日** | 每日零時 |

陽曆陰曆規則相同。此規則與 `123諮商版生命藍圖(mail).xlsx` 的 366 天逐日表 **366/366 全數吻合**，該檔已授權作為黃金樣本。

**要求：**

1. 在 `src/lib/numerology/` 建立**單一真實來源**，純函式、零依賴、有型別。農曆表採用 `lunar-vectors.json` 的 `table`。
2. 跑 `numerology-vectors.json`（`golden_from_excel` 366 筆必須全過）與 `lunar-vectors.json`（428 筆必須全過）。
3. **lifeos 改兩處**：流月年份段 `String(fyBase)` → `String(birthY)`（改後實測 672/672 全中）；`LUNAR_DB` 2031 年起的月長碼替換並延長至 2100。流年、流日、月份回退邏輯皆已正確，不要動。
4. `nas-annual-engine` 改兩處（`annual_months.py` 的流月、`numerology.py` 的 `flow_for` 把目標日寫死 12/31）。**2027 報告在這兩處修正完成前不得出貨。**

四處修正的完整對照與驗收條件見《流年流月流日-定版規則與修正》第八、九節。

### 1-2 `baseScore` 把數字分好壞 — 合規衝突

原始碼現況：

```js
function baseScore(n) {
  if ([1, 4, 6].includes(n)) return 82;   // → ☀️ 晴朗
  if ([2, 3, 5].includes(n)) return 62;   // → 🌥️ 陰偶陣雨
  if ([7, 9].includes(n)) return 48;      // → 🌧️ 下雨
  if ([8, 11, 22].includes(n)) return 68;
  return 60;
}
```

流年 7 或 9 的人會長期看到「下雨」。這違反品牌規範的「五型無好壞」，也踩到 NAS 第一層禁用的「這個數字就是不好」。

**已定案：移除分數制（原 B 案）。**

- 刪除 `baseScore`、`computeOverallPercent`、`weatherBand` 與百分比顯示。
- 改為直接呈現當日流日的型態，例如「今天你走在流日 7：內省期」加一句話。
- **九種流日的用語與邏輯，直接沿用 365 能量氣象台**，不另外發明一套。2027 報告的流月描述也用同一組詞，確保三個產品出口講同一種話。
- 不得出現暗示吉凶的字詞，不得自創狀態名詞。

### 1-3 生命功課等級（1–7 級）公開呈現

既有 `/nas/calculator/` 已公開顯示陽曆與陰曆的生命功課等級，並說明「級數不是分數，七級不比一級好」。先前「免費頁不顯示等級」的限制已撤銷。Erick 已裁定合併到 `/nas/calculator/`：保留既有等級說明，並在同頁呈現流年、流月、流日與月信入口。`/nas/life-number/` 從未上線，不建立該路由或轉址。

## 2. 計算核心移植

從 `lifeos` Worker 取出下列函式，原樣移植，**不得趁機重構演算法**：

`sumDigits`、`calcPath`、`calcSoulLevelFull`、`LUNAR_DB`、`getLunarStruct`、`calcFlowsWithTarget`、`calcNumerology`、`calcNumerologyWithTarget`、`parseDateStr`

### 必須保留的行為（容易改錯）

- **流年在生日換，不是 1/1 換。** `calcFlowsWithTarget` 裡：若 `targetM < birthM`，或同月但 `targetD < birthD`，流年基準年要減 1。
- **流月在生日的「日」換。** 若 `targetD < birthD`，流月基準月減 1，為 0 時回捲成 12。
- **補零。** `String(month).padStart(2,'0')`，月份 10 以上與個位數月份都要正確。
- **`calcPath` 第一個元素補零、其後不補**，輸出形如 `20/2`、`-33/6`。
- **閏月。** `LUNAR_DB` 的 code 欄位格式是 `閏月號|13位月份天數碼`，`getLunarStruct` 的閏月推進邏輯要照搬。
- **時區固定 `Asia/Taipei`。** 現行用 `new Date(new Date().toLocaleString("en-US",{timeZone:"Asia/Taipei"}))`，移植時改用更穩健的寫法但結果必須相同。
- **生日早於該年農曆新年要回退一年**（`getLunarStruct` 裡 `offset < 0` 的分支）。

### 回歸測試（不可省）

建 `src/lib/numerology/__tests__/vectors.json`，至少涵蓋：

- 月份 10、11、12 各一組
- 個位數月份、個位數日期（測補零）
- 生日落在農曆新年之前（1 月上旬出生）
- 閏月年份出生（參考 `LUNAR_DB` 中 `code` 前綴非 `00` 的年份，例如 1984 閏10、2033 閏11、2023 閏2）
- 今天剛好是生日、生日前一天、生日後一天（測流年流月邊界）
- `LUNAR_DB` 邊界：1900 與 2050
- 超出表範圍（1899、2051）→ 必須優雅失敗，不可拋例外

**上線條件：舊 Worker 與新模組對同一批輸入，陽／陰主命數、流年、流月、流日全部一致。** 寫一支腳本同時打舊 Worker 的 `mode:"report"` 與新模組，逐欄比對。

### 需要伺服器的部分

只有 OpenAI 呼叫。保留在 Worker 或改用主站的 serverless function 皆可，但 **API key 不得進前端 bundle**。

## 3. 頁面結構 `/nas/calculator/`

**單頁向下捲，不要 tab。** 現行 lifeos 是四個 tab 的工具型結構，教育內容藏在 tab 後面，未轉換的訪客和爬蟲都讀不到。

```
① 首屏：價值主張 + 生日輸入（零摩擦，不擋 email）
② 結果：兩個主命數 + 各自意義 + 陽陰落差那一句
③ 完整度提示：「你現在看到的是六成」
④ 當月流月（Email 牆）→ 月信訂閱
⑤ 教育＋銷售：為什麼是生命數字 / 解決什麼問題 / 定位為什麼重要
⑥ 平衡空間與艾瑞克（信任）
⑦ 下一步：2027 流年報告 / 主課 / 一對一
```

①–④ 個人化；⑤–⑦ 通用內容，**必須進預渲染 HTML**，否則爬蟲與未輸入生日的訪客什麼都讀不到。

### ① 首屏

鉤子用這個方向（不要宣稱「唯一」「市面僅有」）：

> 你以前算過生命數字嗎？那算的是哪一條？

承接：大部分人只算了最後一層，而且只算了一條軌跡。陽曆是你想成為誰，陰曆是你實際上是誰。

輸入欄位：姓名（選填）、陽曆生日（必填）、農曆生日（選填，留空自動換算）。

### ② 結果

- 陽曆主命數 + **它的意義**（現行版本只顯示 `+20/2` 這種代碼，零解釋，這是目前最大的洞）
- 陰曆主命數 + 它的意義
- **陽陰落差那一句**——三種情形：陽高陰低（說得到做不到）／陰高陽低（做得到說不出口）／陽陰同數（一致，但做不了違心的事）

落差這句是整頁共鳴最強的地方，放在最顯眼位置。

生命功課等級的展示方式，依 Erick 對既有 `/nas/calculator/` 的頁面方案裁定；本規格不再要求隱藏。

### ③ 完整度

只有陽曆約六成、加農曆約八成五、再加出生時分十成。

提示在農曆生日輸入旁、計算前即可看見；相同文案必須出現在 `/nas/calculator/` 預渲染 HTML。

這是最好的轉換機制，因為是系統本來就有的設定，不是人為稀缺。讓使用者自己發現「我只看到一半」。

### ④ 本次流月（Email 牆）

**容器用「使用者自己的週期」，不是日曆月。這是本節最重要的設計決定。**

流年在生日那天換。流月則逐日套用定版公式 `IF(當日 >= 生日日, 本月, 上個月)`，並依計算結果的來源月變化日切分週期。若生日是 31 號，2 月不會另設月底換期：1/31–2/28 取一月、3/1–3/30 取二月、3/31–4/30 取三月、5/1–5/30 取四月。若用日曆月當容器，可能會看到跨越兩個流月的區段。

使用者問的不是「十月是什麼」，是「我現在是什麼」。而「我現在」永遠只有一個數字。所以顯示：

> 你現在走在流月 5
> 這個階段到 10/24，10/25 進入流月 6

一個數字、一個日期，沒有兩段，也沒有簡化掉任何東西。

**必須在頁面上解釋換期規則**，否則使用者會以為算錯（十二月出生的人在十月看到「你走在 2025 的流年」，第一反應是系統壞了）。建議文案，放在流年流月數字旁：

> 生命數字的「年」不是 1 月 1 日換，是你生日那天換。流月依當日套用公式後的來源月變化。

**只給本次流月，不給全年十二個月。** 現行版本免費送出整張十二個月表，形狀跟付費報告的目錄太像，會讓人誤以為已經拿到了。

年度流年的**數字加一句話可以留**（例：「你現在走在流年 3」）——要賣流年報告，使用者得先知道流年存在。留一句製造需求，留一整張表就是送掉商品。

內容 1,500–2,000 字，但**重點是個人化比例不是總長**：

| 段 | 字數 | 內容 |
|---|---|---|
| 1 | 300–400 | **只屬於他的**：陽陰主命數 × 本月流月的交互 |
| 2 | 600–800 | 本月節奏、適合與不適合 |
| 3 | 約 300 | 一個具體的本月行動 |
| 4 | 其餘 | 下月預告 + 2027 報告的自然銜接 |

前 400 字能不能讓人「對，就是我」，決定後面有沒有人讀。

### ⑤ 教育＋銷售

為什麼是生命數字 / 解決什麼問題 / 生命定位為什麼重要。守 NAS 第一層語言。

### ⑥ 品牌

統一描述句一字不差：`平衡空間（No Age Space）的生命數字課程，由艾瑞克主講。`

品牌掛在產品上（平衡空間），艾瑞克掛在人上（講師）。現行 lifeos 整頁只有艾瑞克、沒有平衡空間，要補。

### ⑦ 保留今日提醒

今日提醒**保留**（依 1-2 重新設計）。主命數看一次就夠、教育內容讀一次就夠，但「今天的節奏」是每天能回來的理由。沒有它這頁是一次性工具。

### 延伸提問（AI 問答）

移到 Email 牆後，或本期先關閉。對陌生流量開放有成本也有紅線風險。若保留在前台，必須有頻率限制。

### 欄位

| 欄位 | 必填 | 說明 |
|---|---|---|
| `email` | ✓ | 名單主幹 |
| `name` | ✓ | 稱呼與個人化 |
| `solar_birth` | ✓ | 已有 |
| `lunar_birth` | | 六成 → 八成五 |
| `birth_time` | | → 十成 |

| `unsub_token` | ✓ | 退訂 |

`focus` 是留 email 時的單選題「**你現在最想整理的是什麼？**」，用於名單分眾。**這欄最常被省略但價值最高**——沒有它，後續信只能全名單發同一封，而「工作卡住」和「關係耗損」的人該看的東西完全不同。

四個選項定案文案：

- 工作或方向感，一直抓不準
- 關係裡常常委屈，或覺得耗損
- 想知道自己到底適合什麼
- 卡在某個階段，想不出下一步

維持「描述狀態」而非「標籤分類」——寫「關係裡常常委屈」比寫「關係問題」更容易讓人勾下去。

### 與 `customers` 的關係

`erickfirm-pay` 已有 `customers` 表（目前 0 筆）。訂閱者買了 2027 報告之後會變成 customer。**用 email 當關聯鍵**，不要在兩邊各建一套身分，否則同一個人會有兩筆記錄對不起來。本期只需在名單表留 `email` 並確保格式正規化（小寫、去空白）。

### 合規

明確用途說明、同意勾選（不可預設勾選）、每封信可退訂。個資法該有的不要省。

## 5. 月信訂閱

**不是一次性的當月報告，是每月流月信的訂閱。**

- 留 email 後**立刻寄出當前這一封**
- 之後**在每個人自己的流月換日前一天寄**（不是每月 1 號）
- 每封信涵蓋的是**即將開始的那一個完整流月**（例：10/25–11/24），不是日曆的十一月

為什麼不是 1 號寄：每封信須依個人流月公式推導出的下一個來源月變化日安排；在該日的前一天寄送，信件就能對齊即將開始的完整週期。

附帶兩個好處：寄送量自動攤平到三十天不會單日塞爆；而且這直接決定了下面的額度夠不夠。

**短月處理：** 不把不存在的生日日補到月底。所有日期直接套用定版公式，再逐日偵測流月來源月變化；月信寄送日由變化日往前一天推導。生日 31 號的例子：1/31–2/28 取一月、3/1–3/30 取二月、3/31–4/30 取三月、5/1–5/30 取四月；一年仍形成十二個流月區段。

與 2027 報告的差異要在信裡講清楚：月信是「這個月該注意什麼」（被動、當下），報告是「整年的排程、衝突線、轉角年」（主動、全局）。

### 寄送通道與服務商

**Email 是名單主幹**，不是 LINE。LINE 官方帳號輕用量只有 200 則且**不可加購**，而「則」是人次——500 人名單群發一次就用掉 2.5 個月額度。中用量 3,000 則（月費 11/1 起調為 1,000 元），高用量 6,000 則（調為 1,400 元）。LINE 的正確用法是**已購用戶與高意願者的服務通道**（一對一回覆不計費），不是名單群發。

**ESP 採用 Resend。** 官方定價（2026-10-24 查證）：

| | 每日上限 | 每月額度 | 支撐名單 |
|---|---|---|---|
| Resend Free | 100 | 3,000 | 約 3,000 人 |
| Resend Pro $20/mo | 無 | 50,000（超量 $0.90/1,000） | 約 50,000 人 |

因為寄送攤平到三十天，每日上限才是真正的天花板。選 Resend 的理由：我們要的是純投遞 API，名單住在 Supabase 當單一真實來源，不需要完整行銷套件；免費層已含自動抑制名單、退信明細、DKIM/SPF/DMARC。

替代選項 Brevo 免費 300/日（約 9,000 人），免費期較長，但付費價格未能從官方頁確認（JS 渲染）。

### 架構與分工

| 層 | 用什麼 |
|---|---|
| 名單 | Supabase `ErickFirm_DB` |
| 排程與編排 | n8n（已確認有 Resend、Brevo、Supabase、Schedule Trigger、HTTP Request 原生節點） |
| 備援排程 | Cloudflare Worker + Cron Trigger |
| 投遞 | Resend API |

**需要人工完成、不可由 AI 代做的**：開 Resend 帳號、取得 API key、將 key 存入 n8n credential、設定寄件子網域（建議 `send.erickfirm.com`）的 SPF／DKIM／DMARC 記錄。

**必要的投遞合規**：每封信必須帶 `List-Unsubscribe` 標頭（法規要求，Gmail 與 Yahoo 亦在技術層面要求，缺少會被降級投遞）；用子網域寄件以隔離主網域信譽，避免影響日常商務信件。

### 內容生產

1,500–2,000 字 × 流月九種 × 要搭配主命數組合，是乘法不是加法。**不要規劃成每月手寫。**

做法：固定骨架 + 可組合段落庫 + 少量 AI 潤飾，**紅線詞寫死在產生管線裡自動擋**。顧問會員的內容工具已經是這個設計，沿用同一套。

## 6. 合規修正清單

NAS 第一層禁用：命定、注定、改命、開運、絕對準、破解命運、你一定會怎樣、這個數字就是不好。另外**「解鎖」「秘密」「破解」也不要用**，會把 NAS 推向算命語感。

不得宣稱「唯一」「市面僅有」「第一」——無法驗證，且與「絕對準」是同一個語感家族。雙軌的說服力來自讓使用者自己對照經驗，不是來自宣稱稀有。

**不判型。** 盤不完整（沒有出生時分、九宮、連線），不得宣告「你是落差型／斷線型」。可用五型的現象語言描述，不得自創狀態名詞。

**不出現感情數。** 單人算不出來（感情數＝兩人主命數相加）。

本次要掃過並修正的既有文案：首屏標語、今日提醒的天氣用語（見 1-2）、AI 問答的 system prompt。
